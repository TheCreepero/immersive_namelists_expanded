# Tooling Backlog

Open problems in `build.ps1`, the tests, the skills and the rules (`docs/inex-agent-guide.md` §1). During a nation's planning or implementation a tooling problem is worked around and gets one entry here. Entries are fixed in a session of their own, and a fixed entry is deleted (git history keeps it).

An entry says what happens, where it was seen, the workaround, and what a fix would look like if that is known.

## Open

### Lints
- **`PLACEHOLDER_ENTRIES` and `LOW_DEPTH` count real numbered entries as placeholders.** An entry that matches the fallback pattern is a placeholder to the lint even when its key is a historical, non-sequential number (`GER_GAR_01`; plain variants such as `GER_Inf_01` are exempt since 2026-10-17), or when the name carries its identity in a suffix (`schwere SS-Panzer-Abteilung %d (I. SS-Panzerkorps)` in `GER_SS_08`). Seen in the German audits of 2026-10-09. Workaround: list the flags under "Kept on judgment". Fix idea: exempt groups whose keys are not a 1..N run, and compare the whole name, not its pattern.
- **`Variant: plain` is given only to a fallback-only group.** A plain variant that keeps official regional titles without nicknames (`ENG_INF_01` "%dth (West Riding) Infantry Division", `ENG_ARM_01`) is not paired with its named group (`ENG_INF_04`, `ENG_ARM_04`, both linked to it), so it keeps `PLACEHOLDER_ENTRIES` and `LOW_DEPTH`. Seen in the ENG audit of 2026-10-25. Workaround: "Kept on judgment". Fix idea: treat any group that a `(Named)` group links to as the plain variant, whatever its `ordered` block holds.
- **No lint compares the number in a name with its ordered key.** A literal name that starts with a number different from its key shows that number in the game, and the fallback later writes the same number again: `POL_AK_01` had `11 = "21 Dywizja Piechoty AK"`, so key 21 became a second "21 Dywizja Piechoty AK"; `POL_LWP_00`, `POL_LWZ_00`, `POL_PSZ_02`, `POL_PSZ_03`, `POL_LDP_00` and `POL_AWL_03` were keyed 1..N with numbered names. Seen in the Poland audit of 2026-10-20. Workaround: read `-NamesOnly -Keys` and re-key the group with `"removeAll"`. Fix idea: a `KEY_NUMBER_MISMATCH` lint for entries whose leading Arabic or Roman number differs from the key, exempting keys past 100 (unnumbered identities by convention).
- **`-Check` refreshes the change table of the wrong plan when two plans for one nation are uncommitted.** It compares with HEAD and writes into one plan (here `2026-10-20-poland-audit.md`), so that plan's table also listed the five groups of `2026-10-20-poland-namelist.md`. Two plans that change one namelist before either is committed also cannot ship as separate commits without interactive staging. Seen in the Poland plans of 2026-10-20. Workaround: one commit for both plans, noted in each ship step. Fix idea: refresh only the plan named in the run (an `-Plan` argument), or the newest plan whose `Status:` is `IN PROGRESS`; have the planning skills check `git status` for an unshipped plan of the same nation and say "ship it first". Since 2026-10-25 a plan that ships moves to `docs/plans/archive/`, so the case is two live plans for one nation.
- **`TODO_COMMENT` matches the Roman numeral XXX in a name.** `ITA_MIL_01` has `XXX Battaglione d'Assalto CC.NN. 'M'` (and XXXIV, XXXVIII, LXXXI, LXXXV), so `-Audit ITA` reports a file-level `TODO_COMMENT` although the file has no TODO note. Seen in the Italy audit of 2026-10-25. Workaround: "Kept on judgment". Fix idea: match `XXX` only in comments and only as a whole word that is not part of a Roman numeral followed by a unit word, or drop `XXX` from the pattern.
- **`-Audit`'s `authored` count counts distinct texts, not entries.** A numbered honorific that several divisions share (`%d-ya 'Vitebskaya' Strelkovaya Diviziya` on six keys of `SOV_INF_01`) counts once, so the SOV audit of 2026-10-25 shows `SOV_INF_01` at 138 authored after the batch writes 242 honorifics over plain keys (280 authored entries), and `AUTHORED` in the summary understates depth work. Workaround: state the per-key count in the plan's "Kept on judgment". Fix idea: count entries whose text differs from the fallback pattern, per key.
- **`UNLINKED_MOBILE` reads the tag, not the role.** `GER_MEC_01_MONARNCHIST` and `GER_MEC_01_COMMUNIST` are independent ideology series but carry `_MEC_` in a vanilla tag. Workaround: "Kept on judgment".
- **`-AuditPlan`'s initial report omits file-level flags** (`IDENTITY_REPEAT`), so its flag count can be lower than `-Audit`'s. Seen in the German audit of 2026-10-09.
- **`SELECTOR_DUPLICATE` compares only the groups of the INEX file.** A vanilla group that INEX does not define stays in the game [NAM-001] and can carry the same selector for the same division types: INEX `FIN_MTN_01` and vanilla `FIN_MTN_02` were both "Mountain Divisions" for mountaineer templates. Seen in the Finland audit of 2026-10-15. Workaround: compare `-InspectVanilla <TAG>` by hand. Fix idea: with HOI4 installed, add the vanilla groups INEX leaves in place to the duplicate check, limited to groups that share a division type.
- **`Vanilla: leaves out` hides vanilla stubs in another format.** `Get-VanillaOverlap` counts an entry that matches vanilla's own fallback as a stub, and reports a stub only when its key lies past a gap. So vanilla's `%d Hohei Shidan` at keys 1-168 of the empty plain `JAP_INF_01` (INEX fallback `Dai-%d Shidan`), and the in-run stubs of `JAP_PAR_01`, `JAP_RGR_01` and `JAP_BIC_01`, are not listed, although they show in the game in vanilla's format. Identities "kept in another list" are counted but not listed, though in a plain variant they still show. Seen in the JAP plan of 2026-10-17. Workaround: a planner script compares every vanilla key the group does not write with the INEX fallback, and the plan writes the fallback over each one. Fix idea: list every left-out vanilla key whose text differs from the INEX fallback, grouped as nicknames and format stubs.
- **`-DryRun` prints no audit summary or flags.** A planner cannot fill "Kept on judgment" from it and has to guess, or rehearse the batch on an export of HEAD (authoring skill, Phase 2 step 3). Seen in the GER plan of 2026-10-25, whose rehearsal gave `FLAGS=8` and `wiki/Home.md: GER group count 22 -> 33` exactly. Fix idea: run the audit on the in-memory result of the batch and print the `AUDIT SUMMARY` and flag lines with the `Dry run OK` line.
- **The identity check of `-Audit` stops at the file.** `Identities shared across groups` compares the groups of one file, so for a nation split over several files (`GER`, `GER_SS`, `GER_ADDITIONAL`) a honorific reused in another file goes unreported. Seen in the GER plan of 2026-10-25, where a planner grep found *'Eifel'*, *'Allgäu'*, *'Chemnitz'*, *'Aachen'* and others already used. Fix idea: compare identities across every file whose key starts with the same country tag.

### Validation
- **`$ValidDivisionTypes` accepts `artillery`, `anti_air`, `anti_tank` and `rocket_artillery`**, which are support-company ids in vanilla (`common/units/artillery.txt`, `anti-air.txt`); the line battalions are `*_brigade`. Eleven groups use them (seen in the SOV audit of 2026-10-15): `SOV_ART_01`, `BRA` (1), `LIT` (2), `SWE` (2), `POL` (5); such a group may never be offered to an artillery template [NAM-004, untested]. Check against vanilla `common/units/` and one game launch before changing the list, then fix those groups in one pass.
- **`$ValidDivisionTypes` rejects line sub-unit ids that a group needs.** Vanilla 1.19.3 has line tank destroyers (`light_tank_destroyer_brigade`, `medium_`, `heavy_`, `modern_`), line artillery (`artillery_brigade`, `mot_artillery_brigade`, `rocket_artillery_brigade`, ...) and uses `armored_car` and `bicycle_battalion` in its own namelists [NAM-004]; `-EditNames` refuses all of them. Seen in the USA plan of 2026-10-15: `USA_TD_01` and `USA_ART_01` fall back to armour tokens with `can_use = { is_ai = no }` (the `GER_PANZERARTILLERIE_DIVISION_01` precedent), and `USA_CONST_01` goes without `armored_car`. Fix with the entry above, after one launch shows which ids a namelist group is offered for.

### Editing
- **`-AddGroup` cannot create a group whose tag does not start with the file's country tag.** It puts `<TAG>_` in front, so vanilla's `SPA_INF_01` and `SPD_INF_01` to `SPD_INF_06` (all in the SPR file) come out as `SPR_SPA_INF_01` and so on, and the vanilla groups are not overridden. Seen in the Spain plan of 2026-10-09. Workaround: a one-line rename after the batch, written as a step of that plan. Fix idea: keep a tag that already has the `<XXX>_<CAT>_<NN>` form, or add a batch key that marks the tag as final.
- **`-Comment` adds a second comment block when a blank line separates the existing one from its group.** `Set-NamelistGroupComment` walks back from the group tag over comment lines and stops at the first blank line, so in a file laid out as banner, comment, blank line, group (all of `zz_INEX_USA_names_divisions.txt`) it inserts instead of replacing. Seen for `JAP_CAV_01` (2026-10-01) and found by reading the code in the USA plan of 2026-10-15. Workaround: the USA plan fixes nine comment lines with a one-off regex replacement step. Fix idea: also take the comment block above a single blank line when nothing else stands between it and the group.

- **A full re-author of an existing file has no one-step batch.** `{ "newFile": true }` refuses a file that exists (`"newFile": zz_INEX_LIT_names_divisions.txt already exists`), the batch has no operation that replaces the header, and `removeGroup` refuses a group while another group's `link_numbering_with` points at it (`cannot remove; link_numbering_with from LIT_MNT_01, LIT_GAR_01 points at it`). Seen in the LIT plan of 2026-10-25. Workaround: the batch's first block removes every old group, dependents first, and a `-SetHeader` step follows the batch. Fix idea: `{ "newFile": true, "replace": true }` that starts the file afresh, or a `"header"` operation for an existing file.
- **`-EditNames` cannot set `for_countries`.** There is no switch or batch key for it, so a shared group (guide §2, Shared Groups; ANZAC in the Commonwealth program) cannot list a second tag through the tool. Seen while setting the shared-group rule on 2026-10-25; no plan needs it yet. Workaround: a one-off regex step after the batch, written in the plan. Fix idea: a `-Countries` switch and `"countries"` batch key that add tags to `for_countries`, refusing a tag the game does not define.
- **`-Link` works only with `-AddGroup`.** An existing group cannot be given `link_numbering_with` (`-Link applies only to -AddGroup`), so a vanilla tag cannot become the named variant of another vanilla tag through the batch. Seen in the SOV plan of 2026-10-15 (`SOV_GTC_01` links `SOV_ARM_03`). Workaround: a one-off regex step after the batch that turns the group's dead `#link_numbering_with` comment into the link. Fix idea: accept `"link"` on an existing group, replacing any link or commented link it has.
  - The workaround no longer finds its target once the group has been edited in the same batch: `-EditNames` drops the dead `#link_numbering_with` comment (and its `# Number reservation ...` line) and leaves an empty double line in its place, and it keeps the template comments `# Names with numbers ...` above `ordered`. Seen in the EST audit of 2026-10-25, whose step 2 inserts the link at the empty line instead.
  - The regex workaround is refused outright: `.claude/hooks/Protect-ProjectFiles.ps1` blocks any shell command that writes into `common/units/names_divisions/` ("a namelist file changes only through build.ps1 -EditNames"), so a step that runs it stops the implementer. Seen in the LAT audit of 2026-10-25. Workaround there: the batch removes the INEX groups and adds them again with `"addGroup"` and `"link"` in one all-or-nothing batch (the LIT re-author pattern), which also drops the template comments. That batch prints `[WARN] Removed group tags: saved templates that used them fall back to default names` although every tag exists again at its end. Fix idea: with `"link"` on existing groups this is moot; until then, compute the removed-tags warning from the file after the batch, not from the `removeGroup` operations.

### Game log
- **`-GameLog` fails while the game is running.** `ReadAllLines` cannot open `error.log` because the game holds it open for writing. Seen on 2026-10-11. Workaround: close the game first. Fix idea: open the log with `FileShare.ReadWrite`.

### Docs
- **`-SyncWiki` does not add table rows for new groups.** It updates existing rows and prints `no row in wiki table (add by hand): <tags>`, although `docs/inex-agent-guide.md` §4, item 3 says it writes the group rows. Seen in the USA plan of 2026-10-15 (11 new groups). Workaround: the plan's docs payload carries the rows verbatim, and a second `-SyncWiki` run checks them. Fix idea: insert the missing rows in file order, after the row of the group that precedes each new group in the namelist.
- **`Get-CountryName` hard-codes the three German wiki pages.** A second multi-file nation needs the same mapping. Fix idea: read the page from the `wiki/Home.md` row of the file.
- **Nothing reports that `wiki/` is ahead of the last wiki push.** `push-wiki.ps1` pushes every pending page, so pages changed by a commit that never pushed go out with the next nation's push, unannounced: the GER push of 2026-10-25 also carried `Contributing.md` and `Engine-Mechanics.md` from `ba54143`. Workaround: guide §4 item 6 (push after any commit that changes `wiki/`). Fix idea: `-Check` compares `wiki/` with the wiki clone's HEAD and warns about pages not yet pushed.
- **The Workshop description grows about 530 characters per nation**: 10,443 of 17,000 with 18 nations (2026-10-09), so the limit test fails around 12 nations from now. Decide on a shorter per-nation form before then.
